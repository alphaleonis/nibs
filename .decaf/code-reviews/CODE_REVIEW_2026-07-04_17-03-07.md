## Findings

### #1 🟡 Medium: New `ui/radio-group-item` primitive bakes in a segmented-control skin instead of the canonical radio look

| | |
|---|---|
| **File** | `web/src/lib/components/ui/radio-group/radio-group-item.svelte:19` |
| **Category** | design / evolution-readiness |
| **Confidence** | 75 |
| **Found by** | design-reviewer (Medium), broad-reviewer (Medium) — corroborated ×2, validation waived |

**Issue:** The fix for prior finding #1 correctly replaced the hand-rolled radiogroup with the bits-ui `RadioGroup` primitive via a new scaffolded shadcn `ui/radio-group/` wrapper — accessibility (`role=radio`, `aria-checked`, roving tabindex, arrow-key navigation, `aria-label`) is now delegated to bits-ui and is complete and correctly wired (confirmed by test-reviewer's mutation probes and typescript-reviewer's contract trace). The residual concern is that the *generic* scaffold `radio-group-item.svelte` hardcodes a SettingsSheet-specific **segmented-control** appearance as its only base class (`data-[state=checked]:bg-background data-[state=checked]:text-foreground data-[state=checked]:shadow-sm rounded-sm px-2.5 py-1 text-muted-foreground hover:text-foreground`), with no radio-dot/circle indicator. Every sibling `ui/` scaffold (`checkbox`, `select-item`, `button`) encodes its primitive's *canonical default* look in the base class; here the base class encodes one call site's *variant*, yet the component sits at the canonical shadcn location and is exported under the generic `RadioGroup`/`RadioGroupItem` names. A near-term second consumer needing a vanilla radio list — plausibly nibs-vmaq's upcoming theme selector in this same Appearance section — imports the "generic" primitive and gets unlabeled pills. Because the checked-state utilities are variant-prefixed (`data-[state=checked]:*`, `hover:*`), `tailwind-merge` won't strip them via a plain `class` override, so that consumer must fork the component rather than reuse it.

**Severity note:** Medium, non-blocking. No functional/accessibility bug — the current single call site is correct and the in-file comment documents the segmented design as intentional. The cost is purely architectural (a naming/location promise the primitive can't yet deliver). consistency-reviewer separately judged the deviation *disclosed and acceptable* given that in-file comment, so this is a reasonable-to-defer tradeoff, not a defect.

**Fix:** Keep the `ui/` primitive neutral (canonical shadcn radio defaults) and move the segmented-control skin to where it belongs — either pass the pill classes per-`Item` from `SettingsSheet.svelte` via the `class` prop, or introduce an app-layer `SegmentedControl.svelte` composed over a canonical `ui/radio-group`. If the team prefers to accept the tradeoff, a one-line follow-up nib noting "radio-group-item is currently segmented-only; generalize before the next radio consumer (nibs-vmaq)" would preserve the decision.

## Minor Findings

### Testing Gaps

- `web/src/lib/components/SettingsSheet.test.ts:11` — The shared module-level `defaultProps.ondensitychange = vi.fn()` is created once and reused by every test that spreads `...defaultProps` without overriding it, and there is no `clearMocks`/`resetMocks` in `vitest.config.ts` nor an `afterEach` reset, so its call history accumulates across the file. Currently inert (every test that *asserts* on the callback passes its own local `vi.fn()`, correctly shadowing the shared one), so it is a latent hazard, not a live false-positive: a future test added here that asserts `expect(defaultProps.ondensitychange).toHaveBeenCalledTimes(n)` would silently inherit prior tests' call history and become order-dependent. Fix: make `defaultProps` a factory (`const defaultProps = () => ({...})`) or drop the spy from it entirely. (test-reviewer, Low)
