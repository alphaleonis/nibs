## Findings

### #1 🟠 High: Row-density selector is a hand-rolled radiogroup with no keyboard navigation

| | |
|---|---|
| **File** | `web/src/lib/components/SettingsSheet.svelte:53` |
| **Category** | accessibility / convention-violation |
| **Confidence** | 100 |
| **Found by** | broad-reviewer (High), quick-reviewer (High) |
| **Validation** | confirmed |

**Issue:** The density control is built from a plain `<div role="radiogroup" aria-label="Row density">` wrapping two `<button type="button" role="radio" aria-checked={selected} onclick={...}>` elements (lines 53-74). There is no `onkeydown` handler and no roving `tabindex`, so it does not implement the WAI-ARIA radiogroup keyboard pattern its own `role` attributes promise: both buttons are independent tab stops and arrow keys do nothing. This is a concrete accessibility regression versus the retired `DropdownMenu.RadioGroup`/`RadioItem` implementation, which got arrow-key navigation and roving focus for free from bits-ui. It also violates CLAUDE.md ("Use shadcn components for all new UI primitives ... rather than hand-rolling"). Validator confirmed bits-ui already ships a `RadioGroup` primitive at `web/node_modules/bits-ui/dist/bits/radio-group/`; the repo has no standalone shadcn `radio-group` wrapper yet (only a `DropdownMenu`-coupled one), so the fix requires scaffolding one — that affects fix scope, not the finding's validity.

**Fix:** Scaffold a shadcn `radio-group` (mirroring how `ui/sheet/` was scaffolded in this same change) or use bits-ui `RadioGroup.Root`/`RadioGroup.Item` directly, wiring `value={rowDensity}` / `onValueChange`. The segmented-control styling can be preserved by styling the `RadioGroup.Item`s.

### #2 🟡 Medium: Sheet emits `aria-modal="true"` while being designed non-modal

| | |
|---|---|
| **File** | `web/src/lib/components/SettingsSheet.svelte:31` |
| **Category** | accessibility / design |
| **Confidence** | 100 |
| **Found by** | broad-reviewer (High), design-reviewer (Medium) — dissent resolved to Medium |
| **Validation** | confirmed (severity → Medium, siding with the design specialist) |

**Issue:** `SettingsSheet` sets `showOverlay={false}`, `preventScroll={false}`, `trapFocus={false}` so the panel is non-modal (background stays visually visible and pointer-interactive — verified: bits-ui only pointer-locks the body when `preventScroll` is truthy). But the sheet is built on bits-ui `Dialog`, whose `Dialog.Content` **hardcodes `aria-modal="true"`** (verified in `node_modules/bits-ui/dist/bits/dialog/dialog.svelte.js:266`, a literal `readonly "aria-modal": "true"`) with no `modal` option on `Dialog.Root`, and `mergeProps(restProps, contentState.props)` makes that internal value always win — a caller cannot override it. So assistive technology that honors `aria-modal` may scope the user to the dialog and treat the background as inert, contradicting the visual/keyboard non-modal experience.

**Severity note:** Resolved to Medium. The current sheet contains only the density control; no background interaction is required by a screen-reader user while it is open (the live-theme-preview use case that motivates non-modality is a *future* nib, nibs-vmaq). It is a real, fixable latent inconsistency / evolution-readiness concern, not a merge-blocking break for this diff. The design specialist and the validator both landed on Medium; broad-reviewer's High is noted as dissent.

**Fix:** Either (a) accept the tradeoff for now and document it (see #3), filing a follow-up nib to base a genuinely non-modal panel on a non-`Dialog` primitive (e.g. a `role="region"`/`complementary` landmark or Popover) before the live-preview theme work lands; or (b) switch the primitive now. Do not attempt to override `aria-modal` via props — verified impossible.

### #3 🟡 Medium: Non-modal override flags carry no rationale in code

| | |
|---|---|
| **File** | `web/src/lib/components/SettingsSheet.svelte:31-36` |
| **Category** | knowledge-preservation |
| **Confidence** | 75 |
| **Found by** | knowledge-reviewer (MUST), broad-reviewer (Medium) |
| **Validation** | confirmed |

**Issue:** `showOverlay={false}`, `preventScroll={false}`, `trapFocus={false}` are three coordinated overrides of modal defaults (verified: `sheet-content.svelte` defaults `showOverlay=true`; bits-ui `Dialog.Content` defaults `trapFocus=true` and `preventScroll=true`), with no adjacent comment explaining why. The only trace of intent is a test-file comment describing the *behavior*, not the *reason*. The repo's other dialogs (`EditorModal`, `ConfirmDialog`) are modal, so a future maintainer/agent seeing three modal defaults individually flipped off — with no signal it is intentional — can easily "restore" them for consistency and silently break the non-modal design (which exists specifically so a future live theme preview stays unobstructed).

**Fix:** Add a short forward-looking comment above the flags, e.g.:
```svelte
<!-- Intentionally non-modal (nibs-8fj2): no overlay, page stays scrollable,
     focus not trapped, so the table behind stays visible/interactive while the
     user previews settings (row density now; live theme preview later, nibs-vmaq).
     Do not restore showOverlay/preventScroll/trapFocus to their modal defaults. -->
```

### #4 🟡 Medium: "Non-modal" tests don't exercise the props that make the sheet non-modal

| | |
|---|---|
| **File** | `web/src/lib/components/SettingsSheet.test.ts:88-99` (also 15-34) |
| **Category** | false-positive-test |
| **Confidence** | 75 |
| **Found by** | test-reviewer (High) — severity → Medium |
| **Validation** | confirmed (severity → Medium) |

**Issue:** The test file frames assertions around the "non-modal" design, but only the overlay-absence check (`document.querySelector('[data-slot="sheet-overlay"]')` is null) actually differentiates non-modal from modal — it verifies `showOverlay`, not `trapFocus`/`preventScroll`. Validator confirmed against bits-ui source that (a) Escape-closes is default `Dialog` behavior for both modal and non-modal (`EscapeLayer` is not gated on `trapFocus`), and (b) `compact.focus(); expect(compact).toHaveFocus()` only proves a native enabled `<button>` accepts programmatic focus — it never Tabs past the dialog boundary, so it does not prove focus is un-trapped. Consequence: reverting `trapFocus={false}` or `preventScroll={false}` to their trapping/locking defaults would fail **no** test in the file — the tests give false confidence about the non-modal contract.

**Severity note:** Medium (down from High): production behavior is currently correct and the overlay assertion covers one real facet; this is a partial-coverage gap, cheap and local to close.

**Fix:** Repurpose the redundant second Escape test into a real trap/scroll probe:
```ts
it("does not trap focus (trapFocus={false})", async () => {
  render(SettingsSheet, { ...defaultProps });
  await user.click(screen.getByTitle("Settings"));
  await user.tab(); await user.tab(); await user.tab(); await user.tab();
  expect(document.activeElement).not.toHaveAttribute("data-slot", "sheet-close");
});
it("does not lock body scroll (preventScroll={false})", async () => {
  render(SettingsSheet, { ...defaultProps });
  await user.click(screen.getByTitle("Settings"));
  expect(document.body.style.pointerEvents).not.toBe("none");
});
```
