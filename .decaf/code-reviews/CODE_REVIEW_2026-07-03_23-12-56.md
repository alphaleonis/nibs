## Findings

### #1 🟠 High: `navigateToNib` idempotence guard skips `selection.select()` entirely → stale `focusedNibId` can misdirect Delete/Edit to the wrong nib

| | |
|---|---|
| **File** | `web/src/lib/composables/useHistoryNav.svelte.ts:47` |
| **Category** | correctness / state-desync |
| **Confidence** | 75 — **validated: CONFIRMED** (corroborated by design-reviewer) |
| **Found by** | quick (High), design (High); finding-validator CONFIRMED |
| **Pre-existing** | No — new regression from routing row/title/dblclick through `nav` |

**Issue:** `navigateToNib(id)` runs `if (selection.selectedNibId === id) return;` **before** `selection.select(id)`. But `select()` (`selection.svelte.ts:10-15`) is a *full resync* — it sets `selectedNibId`, `focusedNibId`, `selectedIds`, **and** `anchorId`. The guard gates the entire body on just one of those effects (`selectedNibId`), so re-navigating to the already-open nib skips the focus/anchor resync.

Keyboard arrow-nav (`useKeyboardNav.svelte.ts:54,58,68,73,89`) calls `selection.focus()` (`selection.svelte.ts:23-25`), which moves **only** `focusedNibId`, leaving `selectedNibId` on the open panel nib. `getActionTargetIds()` (`useKeyboardShortcuts.svelte.ts:49-55`) then **prioritizes `focusedNibId`** for Delete/Backspace/Edit. Reproduced sequence (every step an ordinary interaction):

1. Click row X's title/row → `navigateToNib(X)` → panel opens on X, `focusedNibId=X`.
2. Press ArrowDown → `focus(Y)` → `focusedNibId=Y`, `selectedNibId` still X, panel still shows X (DetailPanel is a non-modal side pane; the tree stays interactive).
3. Click X's row again → `navigateToNib(X)` → guard true (`selectedNibId===X`) → early return → `focusedNibId` **stays Y**.
4. Press Delete → `getActionTargetIds()` returns `[Y]` → confirm dialog fires with a **generic message that names no nib** (`useKeyboardShortcuts.svelte.ts:62-68`) → the user deletes Y while looking at X.

Before this feature routed clicks through `nav`, a plain row/title click called `selection.select()` **unconditionally** and resynced focus on every click, so this drift could not survive a re-click. The confirm dialog's failure to name the target removes the last chance to catch it, and delete is irreversible.

**Fix:** Decouple the two responsibilities the guard conflates — gate only the `history.pushState` on `selectedNibId === id`, and always call `selection.select(id)` (exactly what `handlePopState` already does, guard-free):
```ts
function navigateToNib(id: string) {
  if (selection.selectedNibId !== id) history.pushState({ nibId: id }, "", nibUrl(id));
  selection.select(id);
}
```
Add the regression test named in Minor/Testing Gaps (#F) to lock it in. Note the default `makeTestContext` nav stub (`contexts.ts`) omits the guard, which is why no existing component test exercises this path.

### #2 🟡 Medium: Multi-select collapse-to-one opens/closes the detail panel without a history push — URL/history desync; guard comments overstate the "selection only flows through nav" invariant

| | |
|---|---|
| **File** | `web/src/lib/composables/useHistoryNav.svelte.ts:42-47`; `web/src/lib/components/TreeTable.svelte:337-340`; `web/src/lib/selection.svelte.ts:31-70` (unchanged) |
| **Category** | logic / state-desync + knowledge (invariant overstated) |
| **Confidence** | 75 — **validated: CONFIRMED** |
| **Found by** | knowledge (SHOULD), adversarial (Low); finding-validator CONFIRMED |
| **Pre-existing** | Collapse-to-one behavior predates the diff; the *comments asserting the invariant* were added this round |

**Issue:** The new comments assert "detail-panel navigation flows only through nav" and frame multi-select as orthogonal to the panel ("bulk-selection gestures — intentionally NOT routed through nav, so they record no Back/Forward history entry"). But `toggleSelect` (`selection.svelte.ts:43-44`) and `rangeSelect` (`65-66`) **set `selectedNibId`** — opening the panel via the `panelOpen` derived — whenever the selection collapses to exactly one, and set it to `null` (closing the panel) otherwise. Neither touches history. So a "multi-select" gesture *does* open/close the single-nib panel, without a history entry — the exact desync the invariant claims is impossible. Two validated, ordinary-gesture traces:

- **URL frozen:** Ctrl-click nib A with nothing selected → collapses 0→1 → panel opens on A, URL stays `/`, no history entry. A later `navigateToNib("A")` on A's title early-returns at line 47 (`selectedNibId === "A"`) and never pushes `{nibId:"A"}` → URL/history permanently stuck; refresh/share loses A.
- **Dead Back press:** `navigateToNib(A)` pushes `{nibId:A}` → Ctrl-click A toggles it off (1→0, panel closes, no history write) → plain-click A again pushes a **duplicate** `{nibId:A}` → the first Back lands on the identical middle entry and does nothing visible.

This is the same class the prior review flagged as intentional (#6), but the collapse-to-**one** case genuinely opens the panel, so it is not covered by the "bulk gesture, no panel" framing the comment implies.

**Fix:** Either (a) reconcile history in `toggleSelect`/`rangeSelect` when the selection collapses to a single (or zero) `selectedNibId` — via `nav` `replaceState` to the resulting `{nibId}` / clean path — so URL and history top always match `selectedNibId`; or (b) correct the comments to state the real boundary: multi-select records no history entry, **but** collapse-to-one/zero still opens/closes the panel without a push, so the `selectedNibId === id` guard is **not** sound across those paths. If (b), cite nibs-58c3 and mark it an accepted residual desync.

## Pre-existing Issues

### P1 🟠 High: Ensure-visible ancestor walk has no cycle guard — a parent cycle in `allNibs` spins a synchronous infinite loop

| | |
|---|---|
| **File** | `web/src/lib/components/TreeTable.svelte:181-186` (the `while (current?.parentId)` walk) |
| **Category** | resource-management / robustness |
| **Confidence** | 50 |
| **Found by** | adversarial (High, `pre_existing: true`) |

**Issue:** The ancestor-expansion walk `while (current?.parentId) { next.delete(current.parentId); current = nibMap.get(current.parentId); }` has no visited-set guard. A cycle in fetched parent data (A.parentId=B, B.parentId=A) makes it walk A→B→A→B forever, freezing the tab. The sibling `buildTableData` (`tableData.ts:63-69`) *does* guard cycles with a `visited` set — proving the authors consider cyclic data possible — so this walk diverges from its sibling. The loop condition and termination behavior are **unchanged** by this diff (only the delete body was simplified), so the vulnerability predates the change; nibs' graph layer also rejects cycles server-side, making it latent. Listed here as informational — not verdict-driving.

**Fix (if hardening desired):** Mirror `buildTableData` — `while (current?.parentId && !visited.has(current.parentId)) { visited.add(current.parentId); next.delete(current.parentId); current = nibMap.get(current.parentId); }`.

### Testing Gaps

- `web/src/lib/composables/useHistoryNav.test.ts` — no test for `navigateToNib` switching between two **different** already-selected nibs. Empirically verified: injecting the regression `if (selectedNibId) return;` (truthy instead of `=== id`) leaves **all 17 tests passing**, and `TreeTable`/`App` tests can't catch it either (they use the guard-less `makeTestContext` stub / only ever click the first title). This is the exact test that would have caught finding #1's guard. Add: select A, `navigateToNib("B")`, assert the push happened and `selectedNibId === "B"`. (test-reviewer, empirically verified)
- `web/src/App.svelte:59-63` — no integration test dispatches a real `PopStateEvent` against a mounted `App`, nor asserts `syncFromUrl` ran on mount from an initial `?nib=` URL, so the App-level `$effect` wiring (mount → `syncFromUrl` + popstate listener → Back/Forward end-to-end) is unverified. (test-reviewer, broad-reviewer)

### Residual Risks

- `web/src/App.svelte:260` — deferred pane-collapse `requestAnimationFrame(() => nav.closePanel())` is guarded by `if (selection.panelOpen)` only at *schedule* time; if a different nib is opened before the frame fires, the stale rAF pushes a spurious `{nibId:null}` history entry and closes the just-opened panel. The spurious-history-push is genuinely **new** (old code called `selection.close()` with no history side effect). **Validated real in code but effectively unreachable** via normal UI — `onCollapse` fires only during a captured resize-handle drag, so a distinct nib-open cannot interleave within the ~16ms window. Cheap defensive fix: capture the id at schedule time, re-check at fire time. (adversarial-reviewer; validated CONFIRMED, reachability-downgraded)
- `web/src/lib/composables/useKeyboardNav.svelte.ts:12,110` — `navigateToNib?` is an **optional** dependency with a silent fallback to `selection.select`. The fallback opens a nib **without** a history push, re-introducing exactly the bypass nibs-58c3 exists to eliminate; a future second caller that forgets the param gets no compile error. The sole current caller always passes it and `nav` is always in context, so the fallback is dead defensive code that only serves as a trap. Consider making it required (drop the `?` and `??`). (design-reviewer)
- `web/src/lib/components/TreeTable.svelte:173` — the effect clears a pending deep-link only when `!$result.fetching`, encoding the hidden assumption that `fetching === false` ⇒ the *complete* nib set is loaded. Holds today (single query, client-side filtering), but pagination/windowed loading would make a valid deep-link to a not-yet-loaded nib get cleared as "genuinely absent." Latent evolution risk; gate on an explicit "dataset complete" signal if pagination lands. (design-reviewer)

### Considered But Not Flagged (all agents)

- **Prior round #1 (ensure-visible infinite loop on filtered-out target) — resolved & not reintroduced.** The `sameSet(next, collapsedIds)` guard clears the pending request when ancestor-expansion can't change visibility. `next` is built solely by deletions from a copy of `collapsedIds`, so it is monotone non-increasing; branch (e) is reached only when `next ⊊ collapsedIds`, strictly shrinking it each pass, bounded below by 0 → terminates (adversarial produced a formal QED). Regression test "settles (does not loop)…" passes; empirically, reverting the guard makes it fail cleanly (`waitFor` timeout) rather than hang.
- **Prior round #3 (cold-load premature clear) — resolved & not reintroduced.** `if (!$result.fetching) clearEnsureVisible()` preserves the pending request while fetching; the effect re-subscribes via both `allNibs` (`$result.data`) and the explicit `fetching` read, re-running on settle. Regression test "keeps the pending request while fetching…" passes; empirically, reverting the guard makes it fail immediately.
- **Prior round #2 (bypass-desync) — resolved.** Escape, right-click auto-select, context-menu Open, and editor-save all route through `nav`. (The residual guard-skip and multi-select edges are findings #1/#2 above, distinct from the original omissions.)
- **Prior round #4 (`isNibState` unsound guard) — resolved.** Now validates `typeof nibId === "string" || nibId === null`; hostile `{nibId:42}` rejected (tested). Narrowing `state is { nibId: string|null }` is sound (`!state` short-circuits before `"nibId" in state`, avoiding a `null` TypeError). `history.pushState` structured-clones its data, so no Proxy/getter TOCTOU in the real popstate path.
- **Prior round #5 (factory/accessor name collision) — resolved.** Factory is `createHistoryNav`, accessor is `useHistoryNav()`, matching `createConfirmDialog`/`useConfirmDialog`. File renamed to `.svelte.ts` (consistent with rune-free `useKeyboardNav.svelte.ts`). `HISTORY_NAV_KEY = 'nibs:history-nav'` matches the kebab-case convention. All imports resolve (grep + `tsc` + build clean); no leftover old-name references.
- **`handlePopState(e: {state: unknown})` vs `addEventListener("popstate", nav.handlePopState)`** — type-sound under `strictFunctionTypes`; `PopStateEvent.state: any` structurally satisfies `{state: unknown}` and is funneled through `isNibState`. `nav.*` closures never reference `this`, so bare-reference passing is safe.
- **`handlePopState` empty-string `nibId` via `if (id)` truthiness** (typescript, conf 50) — `{nibId:""}` passes `isNibState` but is then coerced to "absent" (close) by truthiness rather than treated distinctly; inconsistent with `nibIdFromSearch` normalizing `""`→`null`. Not reachable from code this module produces (only foreign `history.state`); minimal impact. Suppressed (Low @ 50 < gate).
- **Editor-save routed through `nav` (un-enumerated site)** (spec, Low) — within the "detail-panel nib navigation" scope; the `selectedNibId===id` guard suppresses a spurious entry when saving the already-open nib; intent documented in-code. Defensible, not scope creep.
- **AC3 deep-link to a filtered-out/archived nib doesn't scroll** (spec, Low) — expected: the nib isn't rendered, and the spec doesn't require overriding the user's filter. Panel opens; no crash/loop (guards clear cleanly).
- **`makeTestContext` default nav stub omits the guard** — it's *more* faithful than production (always resyncs), which is precisely why finding #1 has no failing test today. Test-double fidelity concern, not a production gap.
