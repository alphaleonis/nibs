## Findings

### #1 🟡 Medium: `onCollapse`'s inner `panelOpen` re-check is redundant and does not close the round-2 different-nib residual it appears to target

| | |
|---|---|
| **File** | `web/src/App.svelte:260` |
| **Category** | race-condition / redundancy |
| **Confidence** | 100 — **validated: CONFIRMED** |
| **Found by** | broad (Medium, mechanism correct); knowledge (High — flagged the same line, but its "load-bearing guard / re-entrant onCollapse" premise was **refuted** by the validator via paneforge source) |
| **Pre-existing** | No — this round changed `onCollapse` from `requestAnimationFrame(() => selection.close())` to `requestAnimationFrame(() => { if (selection.panelOpen) nav.closePanel(); })` |

**Issue:** The round-3 handler is:
```js
onCollapse={() => { if (selection.panelOpen) requestAnimationFrame(() => { if (selection.panelOpen) nav.closePanel(); }); }}
```
`closePanel()` already self-guards its history write (`if (selection.selectedNibId !== null) history.pushState(...)`) and `selection.close()` is idempotent. Two consequences:

1. **Redundant for the benign case:** if the panel was closed by other means before the frame fires, calling `nav.closePanel()` unconditionally is already a no-op (internal guard skips the push, `close()` is idempotent). The inner re-check adds nothing here.
2. **Does not fix the different-nib residual** (the round-2 Residual the re-check appears aimed at): `panelOpen` is the coarse `selectedNibId !== null` — it is **still true** if a *different* nib B was opened during the rAF window (validated path: drag-collapse of A schedules the rAF, a programmatic/user selection of B flips `selectedNibId` and App's pane `$effect` re-expands, then the rAF fires with `panelOpen` still true). The re-check passes and `nav.closePanel()` wrongly closes B and pushes a spurious `{nibId:null}`. Because pre-round-3 called bare `selection.close()` (no history side effect), this spurious **history push** in the race window is genuinely new this round.

**Reachability:** near-impossible via normal UI — `onCollapse` fires only during a captured resize-handle drag, and a distinct nib must become selected within the single ~16ms frame. Harm is bounded (one wrong close + one spurious history entry a single Back resolves). Hence Medium, verdict-neutral. Recorded so the residual is not lost.

**Note on the refuted competing mechanism:** the knowledge-reviewer argued the inner guard is *load-bearing* (that closing drives the pane to size 0 and re-fires `onCollapse` re-entrantly). The validator refuted this against `paneforge`'s `collapsePane`, which early-returns (`if (paneSize === collapsedSize) return;`) when called on an already-collapsed pane — so App's `$effect`-driven `.collapse()` cannot re-fire `onCollapse`. Deleting the inner check would **not** reintroduce a re-entrancy bug; it is simply redundant.

**Fix:** Capture the identity at schedule time and compare at fire time, which both removes the redundancy and actually closes the residual:
```js
onCollapse={() => {
  if (!selection.panelOpen) return;
  const openedId = selection.selectedNibId;
  requestAnimationFrame(() => { if (selection.selectedNibId === openedId) nav.closePanel(); });
}}
```
Given the near-impossible reachability, deferring this as a follow-up nib is also acceptable — but if kept as-is, drop the redundant inner `if (selection.panelOpen)` and add a one-line comment stating the different-nib race is a knowingly-accepted residual, so a maintainer does not read the re-check as full protection.

## Pre-existing Issues

### P1 🟡 Medium: Keyboard-Delete of the open nib leaves a stale `?nib=<deleted>` URL — refresh/Back re-selects the deleted nib ("Nib not found")

| | |
|---|---|
| **File** | `web/src/lib/composables/useKeyboardShortcuts.svelte.ts:73` (`handleDelete` success branch); same class at `web/src/lib/components/RowContextMenu.svelte:109,131` |
| **Category** | state-desync (composition) |
| **Confidence** | 75 — **validated: CONFIRMED**, reattributed `pre_existing: true` |
| **Found by** | adversarial (Medium) |
| **Pre-existing** | Yes — `handleDelete`'s `selection.clearAll()` was never routed through `nav` in any round; round-3's delta does not touch `useKeyboardShortcuts`'s delete path (only its Escape handler, added in an earlier round) |

**Issue:** Open nib A (`?nib=A`, history top `{nibId:A}`) → keyboard Delete → `handleDelete`'s success branch calls `selection.clearAll()`, which nulls `selectedNibId` (panel closes) but never touches `window.history`/URL (`selection.svelte.ts:90-96`). The URL stays `?nib=A`. On reload/share/Back, `syncFromUrl`/`handlePopState` blindly `selection.select(A)` with no existence check → `DetailPanel` queries the deleted nib and renders the graceful `detail-not-found` state (`DetailPanel.svelte:424`). No crash/loop, just a broken stale reference. The sibling close paths (Escape → `nav.closePanel()`; DetailPanel's own delete button → `onclose` → `nav.closePanel()`) clean the URL correctly, so the delete paths diverge.

**Attribution:** This is a latent gap that has existed since the feature's URL-tracking was introduced (round 1 fixed Escape/right-click/context-menu/editor-save but missed the delete-success `clearAll()`); it is **not** a round-3 regression. Listed here as informational — excluded from the verdict — but a legitimate real bug worth a follow-up nib.

**Fix (when addressed):** After a successful delete whose target set includes `selection.selectedNibId`, route the panel close through `nav.closePanel()` (or push `{nibId:null}` / clean URL) instead of relying on `clearAll()` alone. Apply to both `useKeyboardShortcuts.handleDelete` and `RowContextMenu`'s delete success handlers.

## Minor Findings

### Consistency

- `web/src/lib/composables/useKeyboardNav.test.ts:50` — the new `navigateToNib` harness default is a bare closure `(id) => selection.select(id)`, not a `vi.fn()` spy, unlike its siblings `toggleNode` / `onDragKeyDown` (lines 48-49, both `vi.fn()`) and the sibling pattern in `useColumnResize.test.ts:12` / `useTreeDrag.test.ts:59`. Because the default's observable effect is identical to the pre-change direct `selection.select`, the composable's call into `opts.navigateToNib` is never independently assertable. Fix: `overrides.navigateToNib ?? vi.fn((id) => selection.select(id))`. (consistency conf 100; corroborated by test-reviewer — same root fix as the Testing Gap below)
- `web/src/lib/composables/useHistoryNav.test.ts:62,76` — the two new regression tests omit the `// Regression (nibs-58c3, review #N): <reason>` comment prefix that this same nib's regression tests use in `TreeTable.test.ts:1178,1210`. Add the citation to match the established convention. (consistency conf 75)
- `web/src/lib/composables/useHistoryNav.test.ts:62` — Test A ("switches between two different already-selected nibs") is a valid, non-redundant test, but its comment (`// A regressed truthy guard ... would skip this`) names a *different* hypothetical regression (a truthy `if (selectedNibId) return`) than the round-2 `=== id` early-return; it does **not** catch the round-2 bug (verified: `"a" === "b"` is false, so both buggy and fixed code push+select). Test B (`:76`) is the actual lock. Optional: clarify the comment so Test A isn't mistaken for the finding-#1 lock. (test-reviewer, Low clarity)

### Testing Gaps

- `web/src/lib/composables/useKeyboardNav.test.ts:168` (and `TreeTable.test.ts:730,1016`) — no test verifies that Enter routes through the **injected** `navigateToNib`. The "Enter on focused row selects it" test asserts a true postcondition (`selectedNibId === "nibs-002"`), which the guard-less harness default also satisfies, so a regression of the Enter case back to `selection.select(...)` directly (losing the browser-history push/URL-sync this round hardened) would pass every existing test.
